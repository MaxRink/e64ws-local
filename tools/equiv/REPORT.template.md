# Differential-equivalence harness — Mahlkönig E64 WS HMI

**Target under test:** `HEM-HSG-HMI-S01 V01.16-24` (E64 WS), vendor userspace in the
virtual grinder (`/tmp/virtual-grinder`).
**Deliverable:** `/tmp/equiv` — contract, scenarios, harness, normaliser, baseline
runs and this report. The research repository was only read; all writes are in
`/tmp/equiv` and `/tmp/virtual-grinder/work`.

Confidence tags used throughout: **observed** (read or exercised directly),
**inferred** (derived from observed facts plus a named mechanism), **unknown**
(not established; needs hardware or a reconstruction).

---

## 1. Why this exists

A byte-identical rebuild of `libNgxUi.so` is not achievable without the vendor's
sources, toolchain and signing keys. Equivalence therefore has to be defined at
the *observable behaviour* boundary: the same inputs must produce the same
outputs and the same side effects, in the same order, within the same timing
class. This harness makes that statement executable.

The vendor stack is the oracle. The harness never patches it, and the only
fixtures it adds are disclosed in §7.

---

## 2. Definition: "behaviourally identical"

Let a **scenario** `S` be an ordered list of steps (each step is one input on one
surface). Let `Obs(T, S)` be the **normalised transcript** that target `T`
produces for `S`: a JSONL sequence of records `(seq, step, op, kind, payload)`
plus the step's latency bucket.

> **Definition.** Two targets `T₁` and `T₂` are *behaviourally identical* for the
> suite `{S}` iff, for every scenario `S`:
>
> 1. **Structure** — both produce the same number of records in the same order,
>    with the same `step`, `op` and `kind` for every `seq`. A missing reply, an
>    extra reply, a different close mode, or a different number of frames is a
>    difference.
> 2. **Shape** — every record payload has the same JSON shape: identical key
>    sets at every depth, identical JSON types, identical array lengths,
>    identical enum strings (e.g. `"Idle"`, `"Completed"`, `"E64 WS"`).
> 3. **Value** — every scalar is equal after applying exactly the normalisation
>    rules declared in `normalisers/rules.json`. No other value is ignored.
> 4. **Invariants** — every `assert` step in the scenario passes on both targets
>    (reply type, `refId` echo, `sessionId` stability, persisted values, …).
> 5. **Side effects** — the compared file/sysfs/SQLite snapshots are equal after
>    the same normalisation (LED and backlight values, GPIO levels, `settings`
>    rows, row counts, config hash).
> 6. **Timing class** — each step's latency falls in the same bucket
>    (`<50 ms … ≥15 s`), and no step times out on one target but not the other.
> 7. **Explained exceptions only** — every remaining difference matches a rule
>    in `diffs/classification.json` whose reason is reviewed and whose
>    confidence tag is `observed` or `inferred`. Unmatched differences are
>    **mismatches**; the default is never "ignore".

**Explicitly outside the contract** (cannot be observed without hardware, or is
environment, not HMI): byte-level binary identity, TLS handshake internals and
cipher choice, QML rendering/VNC pixels, physical motor/AGSA motion, RF
behaviour, cloud/MQTT traffic, and the ESP32 firmware itself (the ESP peer is a
fixture shared by both targets).

This is a *strict* definition on purpose: it is cheap to relax one rule with a
written justification; it is expensive to discover later that a "noise" filter
hid a regression.

### Inputs and outputs that the harness treats as comparable

| Class | Inputs | Outputs |
|---|---|---|
| WSS | 52 JSON records on `wss://:9997/?token=`; token presence/absence; `msgId`; malformed frames | reply frame (`<Type>Result`, `refId`, `data`), close code/reason, silent EOF, latency bucket |
| REST | 13 `rest_api` routes, 4 upload pages, session cookie, bearer token, malformed bodies | status, selected headers, JSON body, binary length, side-effect files |
| ESP control | 21 request/response pairs and 4 asynchronous events on `/dev/esps0` (TLV + protobuf) | response frames, `events_tx`, handler effects visible in driver state |
| ESP JSON | HMI→ESP `ping`, `RequestVersion`, `RequestSdioStatus`, `StartFunction`, `requestConfig` on `/dev/ttySTM1` | heartbeat presence and rate class; reactions in `espVersionNo`/`espSdioState` |
| sysfs | writes via actions (LEDs, backlight, gpio, timers) | read-back values |
| files | `/db` (SQLite, config JSON, counters), `/tmp`, `/storage` | file set, content hashes, SQL rows |
| power | reboot via agent/REST | `boot_id` change, time to WSS-ready, post-boot state |

### Where the vendor stack and the contract disagree (recorded, not hidden)

* `RequestNachineInfo` is spelled **Nachine** in the firmware; the contract keeps
  the literal.
* `RequestOnboardingResult`, `WifiStaConfig`, `WifiConfigChangedProcessed` and
  `GbsCreateReport` carry **no `refId`**, unlike every other reply. Asserted in
  the scenarios.
* On a shipped image every `dev=1` record (44 of 52) is rejected by a **silent
  close** (code 1001, no JSON error body). There is no `UnknownType` reply on the
  wire. Asserted in scenario 02.
* `UpdateCpuConfig` is recovered as failure-valued; `UpdateDriverConfig` is
  marked **unknown** (its payload semantics were not recovered and a wrong write
  is destructive).

## 4. Harness

```
/tmp/equiv
├── contract/hmi_contract.json        # 116-row observable contract
├── contract/generate_contract.py     # provenance generator
├── scenarios/*.json                  # 8 scripted scenarios
├── harness/wsclient.py               # dependency-free RFC6455 client (records close/EOF)
├── harness/target.py                 # target adapters: kind=vg | kind=direct
├── harness/runner.py                 # step executor + JSONL recorder
├── harness/normalise.py              # rules from normalisers/rules.json
├── harness/compare.py                # structural + value diff, classification
├── harness/run.py                    # CLI: run | determinism | compare | contract
├── normalisers/rules.json            # the accepted-noise budget (reviewable)
├── diffs/classification.json         # EXPECTED rules + emulation artefacts
├── targets/vendor.json               # vendor stack in QEMU
├── targets/recon.example.json        # how a reconstruction plugs in
└── runs/vendor/<scenario>/           # raw + normalised transcripts, metadata
```

### Run it

```sh
cd /tmp/equiv
. ./vgenv.sh                            # dedicated port block (38082/38443/39997/…)
python3 -m harness.run run --target targets/vendor.json --scenario all --repeat 2
python3 -m harness.run determinism --target vendor
python3 -m harness.run contract > contract.md
```

`run --repeat 2` executes each scenario twice, normalises both transcripts and
writes `runs/<target>/<scenario>/determinism.json`. `compare` is the same code
path with the classification rules enabled:

```sh
python3 -m harness.run compare --baseline vendor --candidate recon
```

### Scenario model

```json
{"id": "s1", "op": "wss", "action": "StartGrindGbw", "data": {"targetWeightGr": 18.0}, "timeout": 10}
{"id": "s2", "op": "wait", "type": "RequestDriverState", "path": "data.grindState", "equals": "Idle"}
{"id": "s3", "op": "capture", "from": "last_reply", "path": "data.sessionId", "as": "sid"}
{"id": "s4", "op": "assert", "source": "last_reply", "path": "refId", "equals": 3}
```

Ops: `wss`, `wss.raw`, `http`, `shell`, `db`, `state`, `esp.event`, `esp.raw`,
`espjson.watch`, `wait`, `reboot`, `mark`, `sleep`, `capture`, `assert`.
Every step is recorded even when it fails — a failed step is data, not an
exception.

### Scenarios

| # | Scenario | Profile | Determinism baseline | Covers |
|---|---|---|---|---|
| 01 | `01_http` | shipped | yes | REST public/auth routes, session lifecycle, uploads side effects |
| 02 | `02_readonly` | shipped | yes | read-only direct commands, dev gate, token policy, sysfs, `/db` |
| 03 | `03_dev_actions` | dev | yes | dev-only direct commands + 30 non-blocking actions |
| 04 | `04_grind` | dev | yes | grind accept path and state polling |
| 05 | `05_persistence` | dev | yes | mutations, reboot, post-restart state |
| 06 | `06_esp` | dev | yes | ESP events, JSON heartbeats, `EspWifiConfig -u` |

and can block or kill the single Qt thread. It is still executed once per target
and its accept/reject replies are compared; see `E-QEMU-ACTUATOR` in
`diffs/classification.json`.

## 5. Normalisation — the accepted-noise budget

Twelve rules, each with a written rationale and evidence tag, in
`normalisers/rules.json`. Summary:

| Rule | What | Why | Evidence |
|---|---|---|---|
| N-TIME | `hmiTime`, ISO/`dd.mm.yyyy` stamps | wall clock is environment | observed |
| N-UUID | `sessionId`, UUIDs | per-database identity; stability asserted separately | observed |
| N-TOKEN | 64-hex bearer tokens | minted per request | observed |
| N-DURATION | `uptime_s`, `t_rel_ms`, elapsed | CPU/scheduler jitter → bucket | observed |
| N-COUNTER | `configId`, `powerOnCycles` | append-only rows (+1 per start/boot) | observed |
| N-MAC | MAC addresses | virtual NIC/DTB | observed |
| N-ADDR | loopback URLs with ports | port block is a harness choice | observed |
| N-IP | IPv4 | QEMU user network | observed |
| N-PID | pids | per boot | observed |
| N-LOGTS | `[sec.usec]` log prefixes | monotonic since start | observed |
| N-EPOCH | epoch integers | run time | observed |
| N-ORDER | `RequestLogMessages.logMessages` | concurrent ring buffer; reduced to count/levels/categories digest | observed |

Everything else is compared verbatim — notably `refId` echo, `data.success`,
enum strings, the 59 config keys, the 48 state keys, sysfs values, DB rows.

Two rules were added only after the baseline proved the noise was real
(`N-COUNTER`, `N-ORDER`); both are documented as **observed**, not assumed.

## 6. Baseline determinism result

<!-- BASELINE RESULTS -->

The strict gate is: *the same scenario, run twice against the vendor stack from
the same restored state, must produce identical normalised transcripts.*

Method: before every run the harness restores `/db` from a snapshot of the
vendor image (`/storage/equiv/db-pristine.tar`), clears transient `/tmp` state,
re-provisions the owner-password fixture and restarts `NgxUiApp`, then waits for
WSS readiness. Without that, `configId`, `powerOnCycles` and the log ring buffer
make every run unique.

## 7. Fixtures and emulation aids (disclosed)

| Fixture | Why | Where |
|---|---|---|
| `FIXTURE-OWNER-PASSWORD` | The shipped DB has no `Role.Owner.LoginData`, so no owner session can be created. Reset inserts a row with `vendor_hash("e64-equivalence")` — equivalent to an owner setting a password in the UI. | `/storage/equiv/owner.sql` in the guest |
| Pristine `/db` snapshot | Removes history between runs; makes the determinism check meaningful. | `/storage/equiv/db-pristine.tar` |
| `/etc/issue` profile switch | Enables/disables the 14-token dev gate (§ `docs/DEV_MODE_AND_LOCAL_CONTROL.md`). | `targets/vendor.json` → `profiles` |
| Dev-only record coverage | 44 of 52 WSS records are unreachable on a shipped image. | scenario 03 runs under `profile: dev` |

Emulation-only behaviour that is **not** vendor behaviour and is therefore
excluded or classified: actuator waits (`E-QEMU-ACTUATOR`), missing ADC sample
stream (`E-NO-LOADCELL`), inability to inject ESP→HMI JSON
(`E-ESP-JSON-INJECTION`), VNC rendering (`E-SCREEN`).

## 8. How a reconstruction plugs in

1. Copy `targets/recon.example.json` to `targets/recon.json`.
2. Point `http`/`https`/`wss` at the reconstruction. TLS is not verified (the
   device certificate is self-signed); the token is appended as `?token=`.
3. Provide adapters — each is an argv list; the harness writes to stdin and
   reads stdout:
   * `mint_token` → prints one 64-hex token accepted by the reconstruction's
     validator (equivalent of `/tmp/tok_<token>`).
   * `shell` → runs a command as root inside the reconstruction's environment
     (ssh, `docker exec -i`, …).
   * `state` → prints JSON shaped like `vg state` for the fields scenarios keep.
   * `reset` → restores pristine state and restarts the HMI.
   * `power`, `esp_event`, `esp_raw` → optional.
4. If the reconstruction runs in the same QEMU image (recommended: replace only
   `libNgxUi.so`/`NgxUiApp` in the app partition), it inherits the vendor
   `lighttpd`/PHP and the same ESP/WSS peers. Reuse `targets/vendor.json` and
   only change the output directory:
   ```sh
   python3 -m harness.run run --target targets/vendor.json --scenario all \
           --repeat 2 --out runs/recon
   python3 -m harness.run determinism --target recon
   ```
   No adapter code is needed, and `compare` works on `vendor` vs `recon`.
5. Run:
   ```sh
   python3 -m harness.run run --target targets/recon.json --scenario all --repeat 2
   python3 -m harness.run determinism --target recon
   python3 -m harness.run compare --baseline vendor --candidate recon
   ```

The reconstruction must be determinism-clean **against itself** before the
cross-target comparison is meaningful; a target that answers differently on two
identical runs cannot be proven equivalent to anything.

## 9. Acceptance criteria for a reconstruction

A reconstruction is accepted iff all of the following hold. Each is machine
checked except AC-1 and AC-9.

| ID | Criterion | Check |
|---|---|---|
| **AC-1** | Boots in the same QEMU device profile and reaches WSS-ready no later than the vendor's measured class. | `wait_ready` in every scenario |
| **AC-2** | Every contract row whose `scenario` is non-null is exercised and produces at least one transcript record. | coverage report vs `contract/hmi_contract.json` |
| **AC-3** | *Self-determinism*: two runs of every deterministic scenario produce identical normalised transcripts. | `run --repeat 2` + `determinism` |
| **AC-4** | *Equivalence*: `compare --baseline vendor --candidate recon` reports **0 mismatches** over all deterministic scenarios. | `compare` |
| **AC-5** | Negative controls match exactly: dev-gated commands on a shipped image close silently (1001, no body); unknown types close; malformed JSON closes; malformed TLV is ignored without killing the channel; HTTP errors keep status and envelope. | scenarios 02, 07 |
| **AC-6** | Persistence matches: `SetLanguage`, `SetSetupWizardState`, config changes and DB rows survive a restart; volatile outputs (backlight, LEDs) reset to the same post-boot values. | scenario 05 |
| **AC-7** | Side effects match: LED/backlight/GPIO values, `settings` rows, row counts, config hash (excluding the append-only id line). | scenarios 02, 03, 05 |
| **AC-8** | Every remaining difference matches a rule in `diffs/classification.json` with a written reason; no rule may be added without evidence and review. | `compare` output |
| **AC-9** | ASLR/stack/heap layout, binary size, symbol table, TLS cipher and rendering are **not** required to match. | manual review |
| **AC-10** | Any change to the reconstruction re-runs the full suite; the mismatch count must stay 0. | CI gate |

Partial acceptance is not defined: a reconstruction that matches 51 of 52 WSS
records is *not* behaviourally identical. It may still be useful, but it must be
reported as a divergence, not as equivalence.

### What the vendor baseline can and cannot prove

* **Proven:** the vendor stack is deterministic under the scripted inputs, so any
  difference observed against a reconstruction is attributable to the
  reconstruction (or to a declared emulation artefact).
* **Not proven:** behaviour that depends on physical hardware (load cell, motor,
  AGSA, fans, ESP radio), on the cloud, or on a real UI interaction. Those
  contract rows are marked `unknown` and must be tested on hardware or against a
  hardware-in-the-loop fixture.

## 10. Findings from building the baseline

1. **Silent rejection is the norm.** Every policy rejection (dev gate, missing
   token, unknown type, malformed JSON) closes the socket with code 1001 and no
   JSON error body. A reconstruction that answers `{"error": …}` is observably
   different.
2. **Four reply types omit `refId`** (`RequestOnboardingResult`,
   `WifiStaConfig`, `WifiConfigChangedProcessed`, `GbsCreateReport`), while the
   rest echo `msgId`.
3. **`configId` advances on every HMI start** (append-only config row, also
   visible as `"id"` in `/db/HsgConfig.json`). Any comparison that includes it
   without normalisation is guaranteed to fail.
4. **Grind commands are accepted but never transition in QEMU**
   (`grindState` stays `Idle`): there is no ADC sample stream. The contract
   therefore asserts acceptance, not motion; the transition is `unknown`.
5. **Hardware-wait handlers can kill the single Qt thread** (reproducibly
   `CalibrateFan1`; intermittently `EspReset`). They are isolated in scenario 08
   and excluded from the determinism gate.
6. **The log ring buffer is history, not output.** Two consecutive vendor runs
   differed in `RequestLogMessages.logMessages`; only its structure (count,
   levels, categories) is comparable.
7. **`SetBacklightBrightness(9)` does not survive a reboot** (comes back as 7):
   brightness is a live hardware value, unlike `SetLanguage`/`SetSetupWizardState`
   which are persisted in `/db`.

## 11. Limits

* ESP JSON injection (ESP→HMI) is not possible without replacing the daemon's
  peer; only HMI egress is observed.
* The UI (Qt VNC) is not compared. Touch input does not exist in the vendor
  userland; VNC pointer injection is emulation-only and out of contract.
* `UpdateDriverConfig` is not exercised (payload semantics unknown, destructive).
* Firmware/ESP flashing paths (`EspFlashApp`, `EspEraseFlash`, `/dev/ttySTM5`)
  are stubbed in QEMU and only their accept path is recorded.
* The harness measures one image (`V01.16-24`). A different firmware version
  needs its own baseline: run the same suite and diff the two vendor baselines.
* Operational note: the vendor HMI occasionally wedges on its first start after
  a fresh image build (it accepts TLS but never answers). `wait_ready` now
  requires three consecutive successful WSS round-trips; if a transcript still
  begins with `wss.open_failed`, restart the app (`/etc/init.d/S90app restart`)
  and re-run that scenario. Scenario 08 intentionally leaves the app dead.
